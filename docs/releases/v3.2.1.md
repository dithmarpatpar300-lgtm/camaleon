# Camaleon v3.2.1 — Multi-file batch + camera JPEG fix

**Date:** 2026-06-11  
**Branch:** `dev`  
**Tag:** `v3.2.1` (when promoted)  
**Engine:** 1.6.0 (JPEG metadata scan limit raised in `core_utils`)

## Summary

Ships **Tier 3.6.0 multi-file batch** on 14 raster transmutator routes, plus critical fixes for **phone/camera JPEGs** with large EXIF segments and batch UX polish after a successful run.

## Multi-file batch (Tier 3.6.0)

- Drop multiple files on supported tool routes (e.g. JPG → PNG).
- Shared options, per-row selection, sequential prepare/transmute, one download per file.
- Strict tool contract: incompatible formats skipped with notice (use Universal transmutator for mixed drops).

## Fixes & improvements (3.2.1)

### Camera / phone JPEG metadata

- **Root cause:** SOF marker often sits **after 64 KiB** of APP1/EXIF data — valid JPEG, not corrupt.
- **Fix:** JPEG metadata scan raised to **512 KiB** in frontend probe and Rust `core_utils` (requires `npm run build:wasm`).
- Camera photos now show resolution/bit depth and convert successfully.

### Batch prepare validation

- Worker **estimate/decode** runs during batch prepare (same safety layer as single-file).
- Invalid files flagged **before** Transmute — not only at run time.

### Post-batch UX

- When all rows are **Done**, primary action becomes **Convert again** with clear hint text.
- Transmute buttons count only **ready/transmutable** rows — no misleading “Transmute N” toast.

## QA exit gate

1. `npm run build:wasm && npm run dev`
2. Batch: drop 5 **camera JPEGs** (4000×3000) on JPG → PNG → metadata visible, all convert.
3. Batch: complete run → **Convert again** visible; no spurious “select a ready file” toast.
4. Single-file: same camera JPEG → estimate passes, transmute succeeds.
5. Regression: small social JPEGs and PNG→JPEG batch unchanged.
