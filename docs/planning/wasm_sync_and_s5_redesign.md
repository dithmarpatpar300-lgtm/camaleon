> **Status:** Proposal → Implementation
> **Author:** OpenCode

> **Version target:** v3.10.0 (MINOR — new UI capability + new subsystem)
> **Engine:** No Rust/Wasm changes (pure TypeScript/Node.js build script enhancement)
> **Depends on:** existing `precache-toolkit.ts`, `cache-status.ts`, `app-update/*` patterns

---

## 1. Problem Statement

Camaleon ships 13 Wasm crates (~12 MB total) cached via a `CacheFirst` service-worker
runtime route on `/wasm/**`. The Wasm binary URLs are **versionless**
(`/wasm/{crate}/{crate}_bg.wasm`) — a new deploy overwrites the same URL path, but
`CacheFirst` serves the **old cached bytes indefinitely**.

### What breaks

| Scenario | Current behavior | Expected behavior |
|----------|-----------------|-------------------|
| Deploy v3.9.0 → v3.9.1 (Wasm changes) | User's SW serves old Wasm forever; no notification | User is notified that engines are outdated; one-click update |
| User cached 11.8 MB toolkit; new build is 12.2 MB | `precacheFullToolkit` skips all URLs (`if (!existing)`) — never refreshes | Sync detects size/buildId mismatch, purges stale, re-caches |
| App update fires (shell purge + hard reload) | `purgeAppShellCaches` **explicitly preserves** `WASM_CACHE_NAME` — stale Wasm survives app update | Wasm sync independently detects and repairs staleness |
| User checks S5 "Offline & cache" | Shows presence-based count (`13/13`) — looks fresh even when stale | Shows sync status (up-to-date / stale / unknown) with last-synced build |

### Root cause

1. **No Wasm version manifest is generated or consumed.** An orphaned
   `wasm-manifest.json` exists in `public/wasm/` (with `buildId`, `version`, per-crate
   sizes) but is gitignored, not generated by `build-wasm.mjs`, and referenced by zero
   source files.
2. **No staleness detection.** `isWasmCrateCached` / `isWasmReady` test **presence** only.
3. **Cache name hardcoded in 3 files** (`sw.ts`, `cache-status.ts`, `app-update/constants.ts`)
   with drift risk.

## 2. Solution Architecture

### 2.1 Wasm Manifest Generation (build-time)

**File:** `frontend/scripts/build-wasm.mjs`

After all `wasm-pack build` calls complete, generate `frontend/public/wasm/wasm-manifest.json`:

```json
{
  "version": "1.8.0",
  "buildId": "<8-hex-chars from hash of crate sizes>",
  "generatedAt": "<ISO timestamp>",
  "totalWasmSize": 12579993,
  "crates": {
    "transmutador_jpg": { "jsSize": 7210, "wasmSize": 1384699 },
    ...
  }
}
```

**buildId algorithm:** `createHash('sha256')` of `"{crate}:{wasmSize}:{jsSize}"` for all
13 crates, take first 8 hex chars. Changes when any crate's binary size changes — a reliable
proxy for content change without hashing the full binary (fast, deterministic).

**Why not hash the full binary?** Each `_bg.wasm` is 0.1–2 MB; reading + hashing 13 files
adds ~1–2 s to the build. Size-based hash is sufficient: two different builds producing
identical sizes for all 13 crates is astronomically unlikely.

### 2.2 Wasm Sync Engine (runtime)

**New files:**

| File | Role |
|------|------|
| `lib/wasm/wasm-cache-constants.ts` | Single source of truth for `WASM_CACHE_NAME` |
| `lib/wasm/wasm-manifest-types.ts` | TypeScript types for manifest JSON |
| `lib/wasm/wasm-manifest-fetch.ts` | `fetchWasmManifest()` — GET `/wasm/wasm-manifest.json` with `no-store` |
| `lib/wasm/wasm-sync.ts` | `useWasmSyncEngine()` hook — state machine, staleness detection, purge + re-cache |
| `lib/wasm/wasm-sync-storage.ts` | localStorage for `lastKnownWasmBuildId`, `lastWasmSyncAt` |

**State machine:**

```
idle → checking → up_to_date | stale | error
                         ↓ (user clicks "Update engines")
                    syncing → up_to_date | error
```

| State | Meaning | UI |
|-------|---------|----|
| `idle` | Not yet checked | "Not checked" |
| `checking` | Fetching manifest | Spinner |
| `up_to_date` | Cached buildId === remote buildId | Green checkmark + "Up to date" |
| `stale` | Cached buildId ≠ remote buildId, or no cached buildId | Amber warning + "Update engines" button |
| `syncing` | Purging old cache + re-downloading | Progress bar |
| `error` | Fetch failed or offline | "Unable to check" |

**Detection flow:**

1. On Settings drawer open (if online + `wasmSyncEnabled`), fetch `/wasm/wasm-manifest.json`
   with `cache: "no-store"`.
2. Parse `buildId`. Compare to `lastKnownWasmBuildId` in localStorage.
3. If mismatch (or no stored buildId): state = `stale`.
4. If match: state = `up_to_date`.
5. User clicks "Update engines": purge `WASM_CACHE_NAME`, re-run `precacheFullToolkit`,
   store new `buildId` + timestamp.

**Sync action:**

```
purgeWasmCache() → caches.delete(WASM_CACHE_NAME)
  → precacheFullToolkit(onProgress)
  → writeOfflinePrefs({ lastKnownWasmBuildId: manifest.buildId, lastWasmSyncAt: now })
  → state = up_to_date
```

**Auto-detect gate:** `wasmSyncEnabled` pref (default `true`). When disabled, the engine
never fetches the manifest — the user can manually trigger a check via the "Check now"
button.

**Polling strategy:** Unlike the app-update engine (2-min poll), the Wasm sync engine
**does not poll**. It checks:
- On Settings drawer open (if online + auto-detect on)
- On explicit "Check now" button click
- After an app update hard-reload (the stored buildId may now be stale)

This is intentional: Wasm changes only happen on deploys, and the app-update engine
already handles deploy detection. The Wasm sync is a **complement**, not a replacement.

### 2.3 Cache Name Centralization

**New file:** `lib/wasm/wasm-cache-constants.ts`

```typescript
export const WASM_CACHE_NAME = "camaleon-wasm-v1";
```

**Files updated to import from it:**
- `lib/offline/cache-status.ts` (currently defines its own)
- `lib/app-update/constants.ts` (currently defines its own)
- `app/sw.ts` (currently defines its own local const)

The SW file (`sw.ts`) runs in a different scope (WebWorker, not DOM) — it cannot import
from `lib/wasm/` at runtime. Instead, the constant is inlined in `sw.ts` with a comment
pointing to the canonical source. The two DOM-side files import directly.

### 2.4 S5 "Offline & Cache" Redesign

**Current problems:**
- 473-line monolithic component diverges from other sections (no `SettingsRow`)
- Custom `StatCard` + progress bars — visually inconsistent with S2/S3/S4/S6/S7/S8
- Information overload: hero status + 3 stat cards + 2 progress bars + mobile warning
- No Wasm sync awareness
- "Fire test" card is text-only filler

**New design principles:**
1. **Use `SettingsRow` pattern** — consistency with all other sections
2. **Compact status header** — single row with connectivity dot + mode + badges (no gradient hero)
3. **Unified cache overview** — one row with shell/engines/storage in a compact inline format
4. **Wasm sync row** — new: shows sync status + "Update" / "Check now" action
5. **Toolkit toggle** — same function, cleaner `SettingsRow` layout
6. **Offline mode** — same function, `SettingsRow` with inline button
7. **Maintenance row** — restore shell + clear cache as footer actions
8. **Remove:** fire test card (low value), mobile warning (moved to toolkit toggle description), separate progress bars (inline in relevant rows)

**New S5 layout (top to bottom):**

```
SettingsSection "Offline & cache"
├── SettingsRow: Status (compact connectivity + SW/network badges)
├── SettingsRow: Cache overview (shell x/total · engines x/13 · size)
├── SettingsRow: Engine sync (status badge + "Update"/"Check now" button + progress)
├── SettingsRow: Full toolkit (SettingsSwitch + inline precache progress)
├── SettingsRow: Offline mode (button toggle, stacked layout)
└── SettingsRow: Maintenance (Restore shell + Clear cache buttons, stacked)
```

**Progress indicators:** Inline within the relevant row — no separate progress bar sections.
When precaching or syncing, the row's description text changes to show progress
(`Downloading… 7/26`).

**Visual style:** Same tokens as other sections — `border-b border-border` rows,
`text-sm font-medium text-text-primary` labels, `text-xs text-text-secondary` descriptions.
Accent color for sync status badges (green = up to date, amber = stale, muted = unknown).

## 3. New Preferences

### 3.1 OfflinePrefs additions

```typescript
export type OfflinePrefs = {
  fullToolkitPrecache?: boolean;        // existing
  precacheCompletedAt?: string;         // existing
  dismissedMobileWarning?: boolean;     // existing
  installPromoSnoozedUntil?: string;    // existing
  // NEW:
  wasmSyncEnabled?: boolean;            // auto-detect Wasm updates (default true)
  lastKnownWasmBuildId?: string;        // last synced manifest buildId
  lastWasmSyncAt?: string;              // ISO timestamp of last successful sync
};
```

### 3.2 Factory defaults

```typescript
offline: {
  fullToolkitPrecache: false,
  dismissedMobileWarning: false,
  // NEW:
  wasmSyncEnabled: true,
}
```

`lastKnownWasmBuildId` and `lastWasmSyncAt` are `undefined` by default (never synced).

## 6. Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| `wasm-manifest.json` not deployed (build script fails) | Sentinel check in build-wasm.mjs; manifest is non-blocking — sync engine handles fetch failure gracefully (`error` state) |
| User offline when sync checks | Engine returns `error` state; UI shows "Unable to check — connect to verify" |
| Purge + re-cache takes time on slow connection | Progress bar in sync row; user can cancel by closing Settings |
| Cache name centralization breaks SW | SW uses inline const (can't import DOM modules); only DOM-side files import |
| Old `wasm-manifest.json` already in `.gitignore` | Keep gitignored (generated artifact); ensure build script always regenerates |
